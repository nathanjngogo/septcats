## 2. SPIKE 结论（协作方向，T19-01）

- **现状风险量化**：模拟现有 LWW 在同块并发下的丢失 —— **文本编辑蒸发 51.6%、单元格写蒸发 46.6%**（200/200 轮全部发生）；根因三层叠加：实体级 LWW（`replay.ts:89`）+ 整对象 upsert（`main/dbview.ts:557`）+ 整字段 patch（`editor/diff.ts:322`）。
- **候选对比**：(a) 纯自研 merge_policy（含字符级 RGA）30–40 人日、正确性风险高 → **不建议**；(b) **混合：Yjs 承载块内容/结构 + op-log 留元数据/DB 值** 10–15 人日 → **推荐**；(c) 整库 Yjs 40+ 人日、推翻一期验收 → **不建议**。
- **融合成本已实测近零**：加密是文件级 AES-GCM（字节层不透明）零改动；段不变量（lamport 严格升序）不受 payload 影响，merger 仅需一个 `crdt_update` 分流口；200 轮密集编辑后全量 update 16.4 KB ≪ 256 KB 段限；Yjs 双端一致率 **100%**（PM 独立复跑原型 3 次 md5 全等）。
- **主要风险**：`SCHEMA_VERSION 1→2` 混跑期，v1 客户端收到含 `crdt_update` 的段会整段 quarantine（`merger.ts:68-85`）→ **必须先完成升级窗口再发 v2 能力**。
