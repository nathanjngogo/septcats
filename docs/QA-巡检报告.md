## Q-1 🔴 Critical（同步功能不可用）— ✅ 已闭环（T28-01，2026-09-19）

**症状**：在编辑器里输入任意内容后，顶栏状态栏由「已同步」变为「同步错误」；此后不再恢复，待同步 op 累积（实测 `pendingOps=3` 稳定不降）。

**根因（已定位，含报错原文）**：

```
E_SYNC_CYCLE_FAILED：同步轮失败：非法段：第 3 个 op 的设备 desktop0001 与段头 dev=01m2vf7cw8vgwtesznzd7dakh5 不符
```

- `apps/desktop/src/renderer/src/pages/PageView.tsx:45` → `const PAGE_ACTOR = 'desktop0001';`（**渲染层硬编码设备 id**）
- `apps/desktop/src/main/index.ts:144` → `const FALLBACK_ACTOR: ActorId = 'desktop0001';`（main 侧兜底，合理）
- 编辑器产出的 op 带 `actor='desktop0001'`，而段头 `dev` 是真实设备 actor → 段校验拒收 → 同步轮失败并保持错误态

**为什么现在才暴露**：T21-01 才把「编辑器 → 落库」真正接通（此前编辑器不落库）；一旦真实编辑产生 op，错误即现。既有的 CRDT 双实例验收脚本未断言同步状态栏，故漏网。

**影响**：协作/多设备同步对**所有含编辑内容**的写入失效（本地读写、搜索、模板均正常）。

**修复方向（PM 裁决）**：设备身份的唯一真源放 **main 侧**——`blocks:commit`（及同路径写入）在物化前把 `op.actor` **改写为本机真实 actor**；渲染层不再携带设备身份（删除 `PAGE_ACTOR`）。附回归测试：渲染层提交带错误 actor 的 op → 物化后段的 `dev` 必须=真实 actor 且同步轮达 `ok`。真机验收：输入内容后状态栏必须「已同步」且 `pendingOps` 归 0。

**修复与复验（rc.4 真机）**：输入内容后 `state:"ok"`、`errors:[]`、`pendingOps:0`、状态栏「已同步 · 刚刚」；段头/op 的 actor 与 lamport.d 全部=真机 actor。**根因勘误**：段校验比对的是 `op.lamport.d`（不只 `actor`），双字段改写才生效。

**复现步骤**：全新夹具启动 → 侧栏「新建页面」→ 在正文输入任意文字 → 观察顶栏状态栏变为「同步错误」；`window.septcats.sync.status()` 返回 `state:'error'` 且 `errors[0].code='E_SYNC_CYCLE_FAILED'`。

**证据**：`docs/mockups/diag-sync-detail.mjs` 输出（状态栏 `同步错误` + 上述报错原文 + `pendingOps:3`）。

## Q-2 🟡 Low（UX）

**症状**：重载/重开应用后，不恢复上次打开的页面，而是落到「未命名」页（`ensureSelection` 取首个可达页）。
**期望**：恢复上次打开的页（同类产品惯例；dogfood「关掉再打开，接着写」的直觉）。
**证据**：巡检 A5b —— `reload 后选中="未命名"`（内容本身未丢：显式打开目标页后内容完整 ✓）。
**建议**：把「最后打开页」写入本地偏好，启动时优先恢复（失败再回落 `ensureSelection`）。属体验改进，非阻断。

**未覆盖（诚实说明）**：AI 助手实际生成（需本地模型在跑，隔离环境未接）、真实网盘多设备同步（需两台设备 + 网盘）、导入向导真实导入大文件、macOS 平台行为。

**探针缺陷 2 项（非产品问题，已修正）**：
1. B 段「转为数据库」点击用了 `force:true`，命中了**视口外**按钮（诊断实测按钮 `y=-40`）→ 判为探针缺陷；改用滚动后常规点击即生效（诊断已验证转换成功：出现「还没有记录 / 新建记录」）。
2. 巡检早期把「重载后编辑器为空」误判为持久化失败；加入判别（先读重载后选中页、再显式打开目标页）后证实**内容完好**（A5 PASS），真实问题仅为 Q-2。

**结论**：产品核心链路（建页/编辑/落库/搜索/模板/回收站/双语/主题）在真机上均可用；**唯一阻断级问题是 Q-1 同步错误，必须修掉才可发 0.3.0**。

## Q-3 🔴 Critical（P0-2，数据完整性）— 由 `packages/sync` 段名碰撞导致静默丢 op

**来源**：T28-01 工程师自查（报告 §4），PM 判定为 P0 并立单 **T29-01**。
**现象**：段名 `(dev, c_from, n)` 可碰撞——迟到低 `c` 的 op 之后的 flush 段与既有段同名；`publishSegment` 的 `ifAbsent` 返回 `'existed'` 被当作成功 → **该批 op 未落盘且无任何错误上报**（状态栏仍显示「已同步」）。
**证据**：夹具账本 4 op / 盘上 2 op / `watermark=3`。
**影响**：跨设备可见性丢失且**静默**，属数据完整性缺陷 → **必须先于 0.3.0 修掉**。
**状态**：✅ 已闭环（T29-01，2026-09-19，rc.5 真机）。段名改为**内容寻址** `seg-<c_from>-<dev>-<n>-<digest8>.jsonl`（同 (dev,c_from,n) 不同内容得不同名，碰撞消解，`core` 零改动）；`publishSegment` 同名必读回比对：同内容幂等成功／异内容改名重写／全宽冲突抛错且 op 留 pending 重试；冲突入 `sync.status().errors` 不再静默。**真机双实例 ALL-PASS 10/10**，核心不变量 `ledger ⊆ disk`：盘上 4 op / 两端账本各 4 / **missing=0**。
