# TASK-T29-01 · 🔴 P0-2：同步段名碰撞导致**静默丢 op**（`packages/sync`）

> PM：Hermes ｜ 优先级 **P0（数据完整性）** ｜ 来源：T28-01 报告 §4（工程师自查发现）+ PM 判定
> 前置：T28-01 已交付（actor 修正；`docs/tasks/TASK-T28-01-report.md`）

## 0. 现象与证据（工程师自查原文，PM 已核）

**段名 `(dev, c_from, n)` 可碰撞**：当一个**迟到且 lamport.c 更低**的 op 之后继续 flush 时，新段会与既有段**同名**；`publishSegment` 以 `ifAbsent` 语义返回 `'existed'` 并被当作成功处理 → **该批 op 实际未落盘**。

**实测证据（T28-01 报告）**：夹具账本 **4 op**，盘上**仅 2 op**，`watermark=3` —— 即中间一批 op 被丢弃且**无任何错误上报**。

**为什么严重**：丢的是同步数据（跨设备可见性），且**静默**——状态栏仍显示「已同步」，用户与 PM 都看不到。属数据完整性缺陷，**必须先于 0.3.0 发布修掉**。

## 1. PM 裁决（修法方向；实现细节你可优化，但下列不变量必须成立）

**核心不变量（不可妥协）**：**已 flush 的 op 永不丢失**；任何段写入冲突都必须被检测并**以新名字重写**或**合并**，绝不允许「当作成功而丢弃」。

1. **段名去碰撞（首选）**：段名从 `(dev, c_from, n)` 改为**全局唯一**形式（例如加入 `c_to` 上界、或段内 op 的 `op_id` 摘要、或单调递增的段序号 + 内容摘要）。要求：**相同 (dev,c_from,n) 复算不再产生同名歧义**——若必须保持兼容，则对既有段名规则**只增**：名字中新增区分字段仍能被现有读取路径解析。
2. **`publishSegment` 语义收紧**：`ifAbsent` 命中同名时**不得**返回成功；必须区分「同名且内容等价（幂等重复发布，可视为成功）」与「同名但内容不同（**冲突**：改新名重写 + 记警告/事件）」。
3. **可观测**：任何 op 未落盘的情形必须留痕（日志 + `sync.status().errors` 或计数），**禁止静默**。
4. **兼容性**：`MIN_SUPPORTED_SCHEMA_VERSION=1` 不回归；既有段文件仍可读（若改段名需保留旧名读取路径）。

## 2. 必须交付的验证（缺一不可）

1. **回归测试（修前红 → 修后绿）**：构造「迟到低 c op → 后续 flush 同名」序列 → 断言**盘上 op 数 == 账本 op 数**、`watermark` 推进到账本末尾、`sync.status().errors` 为空。**报告贴修前红原文**（预期：op 数不等 / 丢 op 计数 > 0）。
2. **不变量测试**：随机/构造序列下「**任何已 flush 的 op 都能在盘上找到**」（属性式断言，≥3 组序列，含并发推送与迟到 op 交错）。
3. **幂等不回归**：同段重复发布（内容相同）仍视为成功且不产生重复数据。
4. **兼容测试**：既有段文件（含旧命名）仍能被读取并重放。
5. **真机**：双实例同网盘夹具下（可用既有 `docs/mockups/cdp-e2e-twin-collab.mjs` 范式）编辑后**两端内容一致**且**盘上 op 数与账本一致**（PM 会复跑）。
6. 门禁：`pnpm -r test`、`pnpm -r typecheck`、双 token 门禁（未动 UI 也应通过）。
