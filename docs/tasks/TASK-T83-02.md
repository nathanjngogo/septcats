## 背景

`apps/desktop/src/main/assets.ts` 提供附件读取（`findHashFile`/请求处理器），
附件存量在 `layout.attachments`（内容寻址：文件名=内容哈希 [+ 扩展名变体]）。
T81-01 的 GC 只清了 db 面的墓碑行；**盘上附件文件从未对账** → 页面被彻底删除后，
其独占附件（不在任何其他页引用）永久占盘。

## 开工侦察（报告 §0 必答四问，逐条给 file:line 实证）

1. **引用面**：附件被谁引用？至少核：块 `content_json`（图片 src 形态、附件块形态）、
   页面封面/图标、`collection`/`record` 字段值、manifest/同步段内的引用、
   便携包清单（`importer` 的 checksums）。**给出一套「从库里读出全部引用哈希」的确定性算法**。
2. **可见性口径**：墓碑页（`alive=0`）的引用算不算「在用」？给出结论与理由——
   建议口径：**回收站页（未到期）与任何 `alive=0` 行都算在用**（保守，宁可留）；
   只有「引用它的页面已不存在于 page 表」才算孤儿。
3. **共享与大小写**：`findHashFile` 已有模糊匹配（扩展名变体）——对账必须按同一
   匹配规则判「引用是否存在」，否则会误删有引用文件（**这是本单最大的误删风险点**）。
4. **既有两段式先例**：复用 T81-01 的「预览→确认」纪律与设置页位点，
   不要新造交互形态；`sync.gc` 开关是否涵盖本项（给出结论）。

## 交付面

- **纯逻辑**：`planAssetGc(referencedHashes, diskFiles, now, opts) → {deletable[], held[]}`，
  与 `planDbGc` 同区同纪律（**删除永远先算清单**）；扣留原因至少含
  `referenced` / `recent`（保护期，避免刚写入尚未落块的附件被误删）/ `unknown`。
- **执行**：main 侧 `runAssetGc()`——只删清单内文件；**删除走回收站或先重命名再删**（给出选择与理由）；
  返回 `{deletedFiles, bytesFreed, held}`。
- **触发**：设置页「同步」区块内，与「清理已删除内容」并列，复用同一预览→确认面板形态。
- **测试**：纯逻辑全覆盖（有引用/无引用/最近写入保护/扩展名变体引用/空目录）；
  执行路径断言「被引用文件逐字节不变」（夹具即真实库形态的脱敏复刻）。

## 硬不变量（违反即整单退回）

- **绝不删任何有引用的文件**（含墓碑页引用、含扩展名变体匹配命中的引用）。
- 对账只读 db + 只读目录列举；**真实库/真实附件目录不可写**（探针与单测一律 scratch 双钉）。
- 删除前必须落一份「本次将删清单」到日志（可核对），且支持取消=零删除。
