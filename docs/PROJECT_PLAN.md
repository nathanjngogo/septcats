## 1. 产品定位与边界

### 1.1 一句话定位

一个**数据完全属于自己、能被任意网盘带走**的块式笔记 + 轻量数据库工具。

### 1.2 与 Notion 的差异（刻意为之）

| 维度  | Notion                  | 砚台                                  |
| --- | ----------------------- | ----------------------------------- |
| 真相源 | 服务端数据库，本地是缓存            | **本地即真相源**，网盘只是可选副本                 |
| 账号  | 必须登录                    | 无账号体系                               |
| 同步  | 自建服务端 + 事件游标            | 借用用户已有网盘的文件同步                       |
| 协作  | 核心卖点                    | 一期不做（用文件同步天然错开写冲突）                  |
| 离线  | 部分可用                    | 全功能可用                               |
| 体积  | 安装包 104 MB / 运行时 228 MB | 目标安装包 ≤ 90 MB，冷启动 ≤ 1.5 s（见 §11 风险） |

### 1.3 为什么"先不考虑生态"是对的

Notion 的价值 60% 在块模型 + 数据库模型（可复制），40% 在协作/API/模板生态（不可复制）。砍掉生态后剩下的正是最难写但也最有用户价值的部分：**编辑手感和数据结构**。所以一期把全部预算押在 §7 的 M2–M7。

## 3. 前置技术事实与由此锁定的架构决策 ⚠️ 最重要的一节

### 3.1 网盘可用性事实（本次实测，非推测）

* 百度网盘开发者门户 `pan.baidu.com/developer` 返回 **404**；`openapi.baidu.com/oauth/2.0/authorize` 仍返回 200（OAuth 基础设施存活，但文件存储 PCS API 权限受限/文档已失效，bypy 项目自证只能访问 `/apps/bypy` 子目录）。
* 夸克开放平台 `open.quark.cn` 实为**小程序开发者平台**，无网盘存储 API；OpenList 社区驱动名称为 "Quark / TV / Open"，靠 **cookie + 逆向 Web 接口**工作。
* 推论：**不存在可依赖的官方网盘文件同步 API**。

### 3.2 决策 D1：传输层走"同步文件夹"，不做 API 逆向

```
应用  →  写入 <同步文件夹>/  （普通文件，原子写）
夸克/百度网盘官方客户端  →  把这些文件搬运到云端  →  另一台设备落盘
另一台设备的应用  →  监听文件出现 → 合并进本地库
```

* 优点：**完全合规**、零服务端成本、网盘选择对用户自由、离线可写（网盘客户端自己排队）、天然支持任意其它同步介质（NAS/WebDAV/坚果云/OneDrive）。
* 代价：**无法即时**（受网盘客户端轮询间隔影响，秒→分钟级）；不能主动推送；同步状态显示是"最后完成时间"而非"实时"；网盘客户端冲突时会生成 `xxx (1).ext` 副本，需我方**幂等命名 + 去重**消化。
* 封号/违规风险：0（对用户而言就是普通文件同步）。
* 我拒绝把 cookie 逆向作为主链路的理由：违反 ToS、接口频繁变动导致产品不可维护、且把用户账号封禁风险转嫁给用户。**保留为实验性可选 provider（默认关闭 + 首次启用弹风险告知），是否做由你单独决策（Q3）。**

### 3.3 决策 D2：同步单元必须是"不可变事件日志"，不能是 SQLite 文件

把 `yan.db` 放进同步文件夹会**必然失败**：SQLite 是二进制随机写文件，A、B 两台机器各改一次后两个 .db 分叉，文件同步只会带来"整库二选一"，丢一侧的全部改动（网盘冲突副本也救不回来）。

因此采用：

```
真相层：append-only 事件日志分段（JSONL，每段 ≤256 KB，命名含 Lamport 时钟+设备ID → 永不重名、永不改写）
       + 内容寻址附件（files/<sha256>，写一次不修改）
物化层：本机 SQLite（从日志重放得出，可随时删掉重建，绝不同步）
快照层：定期写 snapshot-N.json 压缩历史，防止日志无限膨胀
```

* 合并算法 = **集合并**（新段落地就重放），无需三方合并、无需锁、不需要联网协商。
* 这同时解决了 U5（拷文件夹即迁移）和 Q4（未来若换成自建服务端，传输层换 provider 即可，真相层不动）。
* 代价：实现复杂度高于"同步一个 db 文件"，M8 工作量约一半来自这里。**这是不可省的成本**，任何"先同步 db 文件以后再说"的做法都会在第 3 个月返工。

### 3.4 决策 D3：块级 LWW + 冲突副本保留（一期不做 CRDT）

* 每个块独立版本号（Lamport 时钟），文本字段 Last-Write-Wins。
* 检测到同一块双端并发编辑 → **不静默丢弃**，把旧版本落成一块"⚠️ 冲突副本"附在原块下方，用户可见可删（数据零丢失优先于优雅）。
* 一期不引入 Yjs：我们的场景是"同一人错开设备写"，不是多人同屏；Yjs 在 M8 v2 预留接口位（Q5 决定是否提前）。

### 3.5 决策 D4：SQLite 由独立子进程独占

沿用我在 Notion 逆向中验证过的真实设计（其 `SqliteServer.js` 以子进程 + MessagePort 服务多渲染器）：单写者、崩溃隔离、渲染器无法直接摸库。

## 5. 总体架构

```
┌─ Renderer (React) ───────────────────────────────────────────────┐
│ 编辑视图 · 侧栏页面树 · 数据库表格视图 · 命令面板 · 搜索 · 设置   │
│  ↑ 仅通过 window.yan.* 类型化 API（contextBridge）访问一切        │
└────────────────────────┬─────────────────────────────────────────┘
                    preload (contextBridge)
┌────────────────────────┴─────────────────────────────────────────┐
│ Main Process                                                     │
│  生命周期/窗口/标签 · 菜单快捷键 · IPC 路由 · 深链 · 崩溃看门狗    │
│  ├─ DbServer (utilityProcess)  better-sqlite3 独占 · 迁移 · FTS   │
│  └─ SyncEngine (utilityProcess) 段调度 · 合并 · provider · 加密   │
└───┬───────────────────────────────┬───────────────────────────────┘
    │ 真相层读写                     │ 文件读写（原子替换）
    ▼                                ▼
  ~/.yan/yan.db                <同步文件夹>/yan/  ← 网盘客户端搬运
  ~/.yan/attachments/          ├ seg-<lamport>-<dev>-<n>.jsonl.enc?
                               ├ snapshot-<n>.json
                               ├ files/<sha256>
                               └ manifest.json (水位线/设备表/保留窗口)
```

要点：

1. **只有 SyncEngine 碰同步文件夹，只有 DbServer 碰 SQLite。** 单向依赖，无循环。
2. 事件段是"写入即发布"，DbServer 重放后产生 `projection_version`，UI 只读物化视图。
3. 渲染器永不接触文件系统与网络（`nodeIntegration:false`、`sandbox:true`、contextIsolation 开）。

## 6. 数据模型（草案，M3 定稿）

### 6.1 事件（真相层）

```ts
type Op = {
  op_id: string;            // ulid，段内唯一
  lamport: { c: number; d: string };  // 逻辑时钟 + 设备ID，排序与冲突判定
  at: number;               // 墙上时间，仅展示用，不参与排序判定
  actor: string;            // device_id
  target: { table: 'block'|'collection'|'record'|'schema'|'page'; id: string };
  kind: 'upsert'|'delete'|'move'|'reorder'|'patch';
  payload: Record<string, unknown>;   // 字段级差量（patch 时）或整对象（upsert）
  base?: number;            // patch 时的基版本，检测并发
}
```

### 6.2 SQLite 物化视图（表清单）

借鉴 Notion schema 中被验证过的三点：**软删除 `alive`**、**复合主键含归属维度**、**STRICT 表 + 显式索引 + ANALYZE**。

| 表                     | 用途         | 关键列                                                                                                               |
| --------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------- |
| `page`                | 页面（块的宿主）   | id, workspace\_id, title, icon, cover, parent\_id, alive, version, sort\_key                                      |
| `block`               | 内容块        | id, page\_id, type, props(JSON), content(JSON), parent\_id, **sort\_key(Rational)**, alive, version, last\_edited |
| `block_fts`           | FTS5 虚表    | title, body（trigram 分词）                                                                                           |
| `collection`          | 数据库定义      | id, page\_id, schema(JSON: 属性定义), views(JSON), alive, version                                                     |
| `record`              | 数据库行       | id, collection\_id, values(JSON), sort\_key, alive, version                                                       |
| `workspace`           | 工作区        | id, name, root\_page\_id, settings(JSON)                                                                          |
| `favorite` / `recent` | 收藏与最近      | user 侧派生表，**不参与同步**（设备本地，避免噪音事件）                                                                                  |
| `attachment`          | 附件登记       | sha256, name, mime, size, page\_id, sync\_state                                                                   |
| `op_ledger`           | 已重放事件账     | op\_id PK, seg\_id, lamport, applied\_at                                                                          |
| `sync_state`          | 同步水位       | device\_id, last\_lamport, last\_sync\_ok, pending\_ops, conflict\_count                                          |
| `meta`                | schema 版本等 | key PK, value（`user_version` 双保险）                                                                                 |

* **sort\_key 用有理数字符串**（LexoRank 风格）而非整数：插入中间不需要批量重排 → 不会产生"改一个块动 500 行"的事件风暴，这是拖拽排序能同步的前提。
* `recent`/`favorite` 之类"读操作衍生态"刻意排除在同步外（否则每次切页都产生事件，日志会脏）。

### 6.3 同步文件夹布局

```
<SyncRoot>/yan/
  manifest.json            # {schema_ver, device_table, snapshot_watermark, retention, salt_hint}
  seg-000012f7-a3-000004.jsonl[.enc]   # 不可变；一段 ≤256KB 或 ≤500 op
  snapshot-000018.json     # 压缩快照，引用已折叠的 seg 上界
  files/e3b0c442...1f.bin  # 内容寻址附件
```

* 命名含 `(lamport, device, seq)` → 跨设备**不可能重名**，网盘副本 `xxx (1).jsonl` 出现时按内容 hash 去重即可（幂等）。
* 段文件**原子写**（写临时名 → rename），避免网盘抓到半截文件。
* 删除只在 `manifest` 里标 tombstone，真删延迟到 retention 窗口（默认 30 天）后，防"另一台机器还没拿到就被删"。

### M0 工程基建与治理

* **职责**：monorepo（`apps/desktop`、`packages/core`、`packages/schema`、`packages/ui`）、pnpm workspace、ESLint+Prettier+TS strict、`electron-vite` 三进程脚手架、日志器、崩溃上报（本地落盘，无外联）、CI（typecheck/lint/unit/build 双平台）、`vitest` + `playwright-electron` 骨架、CHANGELOG/版本策略。
* **接口**：`packages/core` 导出纯 TS 领域逻辑（不 import electron，可 node 直测）——**这是"同步引擎能被单测覆盖"的前提，属硬性约束**。
* **交付物**：能 `pnpm dev` 起一个空白窗口 + CI 绿。

## 8. 数据流与关键时序

### 8.1 一次编辑

```
按键 → PM 事务 → 块差分 patch Op（M3 生成，带 lamport）
     → DbServer 同事务：写 op_ledger + 更新物化视图 + 更新 FTS（一次 IPC，原子）
     → UI 乐观渲染
     → SyncEngine 订阅本地已提交 Op 队列 → 攒段 → 原子写入同步文件夹
     → 网盘客户端自行上传（我方不感知，直到对端出现）
```

一致性要点：**Op 写入与视图更新在同一事务**，否则崩溃后视图与日志不一致（M3 收敛性测试覆盖）。

### 8.2 启动

`单实例锁 → 读 config → 启动 DbServer（迁移+完整性检查）→ 启动 SyncEngine（后台，不阻塞首屏）→ 打开窗口 → 恢复标签/窗口态（state.json，学 Notion）→ 首次同步轮询`

### 8.3 双端合并

`FSWatcher 静默期(1.5 s) → 扫描新段 → 内容 hash 去重 → 校验 schema_ver → 重放 → 冲突检测 → 更新 manifest 水位 → UI 同步状态刷新`

### 8.4 加密开启后的读路径

`manifest 取 salt → 钥匙串取主密钥 → 解 DEK → 解段 → 校验 AAD(文件名) → 重放`；钥匙串丢失 → 引导输入恢复码，否则明确告知不可恢复（无后门，这是隐私优先的必然代价）。

### 8.5 手工迁移（U5）

设置页"导出便携包" → 生成 `<同步文件夹>/export/<ts>.zip`（含 manifest、全部段、附件清单），新机"导入便携包" → 重放重建 SQLite。

## 10. 安全与隐私设计（一期即实施，不留债）

1. 渲染器 `sandbox:true`、`contextIsolation:true`、`nodeIntegration:false`，CSP 严格，`webSecurity` 不许关。
2. IPC 白名单化（含 SQL 语句白名单，见 M2）。
3. 默认**零外联**：无遥测、无 CDN、无崩溃上报到远端；网络请求只可能来自用户显式配置的 AI provider 与更新检查（可关）。
4. 密钥（AI provider token、网盘相关凭据）只进 OS 钥匙串，不落 JSON；日志与诊断包写盘前正则脱敏。
5. 更新：发布者名 + 自签 feed + sha512 三重。
6. 深链 `yan://` 只接受白名单动作，拒绝任意路径打开。
7. 附件类型黑名单（可执行文件不进工作区）。
8. 破坏性操作（清空回收站、GC 旧段、导出覆盖）先备份再执行，且日志留痕。

## 16. UI 质量系统（红线 · PM 直接负责）
> 用户红线：**「我对 UI 设计的要求很高」**（2026-09-12）。本节是**验收门槛**而非建议：凡 §16 条目 PM 有一票否决权；CodeBuddy 不得「先上线后优化」。

1. **Token 单一来源**：根目录 `DESIGN.md`（Google design.md 规范，PM 编写维护）。CI 门禁：
   `npx -y -p @google/design.md designmd lint DESIGN.md` → 0 error 且 0 contrast-ratio warning。
   组件禁止字面量颜色/字号/圆角/间距，一律 `var(--*)`；审查发现魔法值 = 打回。
2. **Design Read（一句话）**：*安静的、精确的、带一点猫须般灵巧的桌面书写工具* —— Linear 级克制 × 中文编辑部呼吸感。
   Dials（product-UI 变体，非落地页基线）：`DESIGN_VARIANCE 4`（产品 UI 讲纪律）、`MOTION_INTENSITY 4`（动效只服务反馈）、`VISUAL_DENSITY 3`（编辑画布）/ `6`（数据库表格）。
3. **双主题一等公民**：浅色/深色**同时设计、同时验收**；禁纯 `#000`/`#fff`；每个颜色 token 必须给双值；PR 未附双主题截图 = 未送审。
4. **四态必交付**：空态（有构图、指明出口）/ 加载（骨架屏，形似最终布局，禁通用转圈）/ 错误（内联、可重试、说人话）/ 成功。缺任一态即「功能未完成」，不得计入进度。
5. **排版（2026-09-21 老板全局规则更新）**：UI 与正文 = **思源黑体（Source Han Sans / Noto Sans CJK）**，**自托管捆绑**（可变字体 `apps/desktop/src/renderer/assets/fonts/NotoSansSC-wght.ttf`，一份覆盖全字重轴），不依赖系统字体；栈序 `"Source Han Sans SC", "Noto Sans SC", …, "Microsoft YaHei", sans-serif`。正文 16px / line-height 1.75 / 最大 72ch；**等宽（数字/日期/代码）暂保留现状**（老板未指定，如需改另立单）；中英混排规则写进 DESIGN.md prose。**禁止 Google Fonts CDN / 任何在线字体**（离线红线）。落地单：T50-01。
6. **图标**：`@phosphor-icons/react` 单族，全局 `strokeWidth 1.5`，禁混族、禁手绘杂集（品牌猫标例外，走 §17 独立评审）。
7. **动效**：仅 spring（`stiffness≈100 / damping≈20` 家族），仅 animate `transform/opacity`；每个动效须能一句话回答「它表达了什么」（层级/反馈/状态迁移），答不出即删除；全部包 `prefers-reduced-motion` 降级。
8. **细节强制项**：`:focus-visible` 环必须存在且键盘全程可达；`:active` 有 1px 按压位移；圆角体系全应用一致（禁混用）；滚动容器不裁切焦点环；zh-CN 文案无翻译腔、不堆破折号（PM 过一遍 humanizer）；空/错误文案禁止卖萌。
9. **验收机制**
   - **G2**：PM 产出 3 版 DESIGN.md 方向 + 全关键屏 HTML mockup（**编辑器 / 侧栏页面树 / 数据库表格视图 / 命令面板 / 搜索结果 / 设置 / 同步状态 / 冲突清单 / 导入向导 / 回收站**），每屏 2–3 变体，你**逐屏确认**。
   - **G3 起每个里程碑**：附「UI pre-flight」—— 按 §16.1–16.8 逐项自查 + 每屏三张截图（浅 / 深 / 125% 缩放）存 `docs/screens/<milestone>/`。**不通过不呈报、不验收**。
10. **PM 执行 UI 工作时必须加载的技能**：`design-md`、`design-taste-frontend`、`apple-design`、`emil-design-eng`、`animate`、`claude-design`/`sketch`（mockup）、`popular-web-designs`（参照系）、`humanizer`（文案）。
